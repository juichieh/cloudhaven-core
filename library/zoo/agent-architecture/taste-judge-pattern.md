# Taste Judge Pattern

## 類型
Agent Architecture

## 一句介紹
用多個獨立 Judge、分歧討論與信心校準，從大量候選中挑出真正值得繼續投入的方向。

## 核心問題
Agent 已經很擅長大量生成候選，但「能生 100 個方向」不等於「知道哪一個值得做」。當生成成本快速下降後，真正稀缺的能力會從生成轉向判斷：哪些方向有價值、哪些只是看起來合理、哪些值得投入更多時間與資源。

## Pattern
1. 多個獨立 Judge 先各自評估，避免一開始互相污染。
2. 比較分歧，而不是只做簡單平均。
3. 讓 Judge 對爭議候選進行有限度討論或交叉質疑。
4. 要求每個 Judge 回報信心，避免把低信心判斷偽裝成確定結論。
5. 對高價值、高不確定性的候選保留人工或專家升級入口。
6. 把最終選擇結果與後續真實結果回寫，持續校準 Judge。

## 為什麼值得收藏
很適合解決「Agent 可以生 100 個方向，但不知道哪個真的值得做」的下一階段問題。生成能力普及後，競爭優勢會更集中到判斷、排序、下注與停止條件。

## 關鍵限制
Taste 不只是另一個 benchmark。真正的專業判斷往往來自長期經驗、失敗記憶、情境知識、隱性標準與對機會成本的理解。這些東西很難完整形式化，也不一定會被公司、專家或組織願意公開分享。

因此，多 Judge 架構可以降低單一模型偏差，但不能自動製造真正的專業 taste。如果所有 Judge 都來自相似模型、相似資料或相似評估標準，最後可能只是「多個版本的同一種偏見」。

## 競爭含義
當大家都能取得相近的大模型與生成能力後，護城河可能逐漸轉向：

- 私有經驗資料
- 歷史決策與結果
- 專家留下的評估準則
- 哪些失敗值得記住
- 何時該停止
- 何時值得逆勢下注

也就是說，真正難複製的可能不是 Agent 本身，而是累積在 Judge 後面的判斷歷史。

## 適合使用的地方
- AI Scientist / Autonomous Research
- 產品與創意候選篩選
- 投資／資源配置前置研究
- 大量 Agent proposal 的排序
- 實驗優先級決策
- Workflow / Tool / Skill 候選淘汰

## 與其他元件的關係
- **Faraday / research taste**：Taste Judge 可以作為研究方向選擇層。
- **Orchard / Agent Evaluation**：Orchard 偏向建立考場；Taste Judge 偏向決定什麼值得考、什麼值得繼續投資。
- **Agent Escalation Router**：當 Judge 分歧大或信心低時，可升級到更昂貴的 reviewer、multi-agent 或 human expert。
- **Decision Ledger / Prelint**：保留當時為什麼選這個候選，供未來校準。
- **Institutional Skills / Shared Memory**：真正的 taste 可能必須從長期組織經驗中逐步沉澱。

## 觀察指標
- Judge 間分歧是否真的能預測風險或失敗
- 信心是否校準，還是只是模型自信分數
- 多 Judge 是否帶來實際增益，或只是增加 token 成本
- 長期結果回寫後，排序品質是否提升
- 私有歷史資料是否成為核心差異化來源

## 時效性
低。這是一個長期 Agent Architecture pattern，不依賴單一產品週期。

## Cloudhaven 判斷
這隻值得長期觀察。它代表 Agent 系統從「會做事」往「知道什麼值得做」移動，但真正的瓶頸很可能不是 Judge 數量，而是 Judge 背後有沒有真正累積過世界經驗。

> 🦞 龍蝦註：100 隻龍蝦都會提案，不代表有一隻知道哪鍋真的該煮。真正貴的是那個吃過很多次虧、知道哪鍋不要碰的老廚師。
